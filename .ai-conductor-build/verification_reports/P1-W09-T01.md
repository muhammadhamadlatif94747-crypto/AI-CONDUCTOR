# VG-P1-W09-T01 — Correlation IDs Through the Canonical Hierarchy

**Task:** P1-W09-T01 — Thread mission → step → attempt → event →
provider_request → tool_call correlation IDs; no independent ad hoc ID
systems (Phase Manifest P1-W09, AC-04 event shape).

**Status:** ACCEPTED

## Starting condition (audit before touching anything)
Before this task, the hierarchy existed only partially and untyped:
`event.rs::EventContext` had `mission_id`/`step_id`/`attempt_id` as bare
`String`/`Option<String>`, constructed by struct literal at three call
sites (`event.rs`, `event_log.rs`, `chain_anchor.rs` — all test code; no
production caller existed yet). There was no `provider_request_id` or
`tool_call_id` anywhere in the crate, and no single shared type any two
modules were required to agree on — i.e. the exact "independent ad hoc ID
system" risk the Phase Manifest calls out, just not yet manifested as two
*competing* schemes because only one caller existed. Confirmed by
grepping every module for `_id`/`Id` before writing any code; `outbox.rs`
(`intent_id`) and `chain_anchor.rs` (`chain_id`) use bare `String` for
identifiers outside this hierarchy (an intent, a log's chain identity) —
left untouched as out of scope; they are not part of the
mission→...→tool_call chain this task threads.

## Implementation
New module `PROJECT/crates/conductor-kernel/src/correlation.rs`:

- Five newtypes — `MissionId`, `StepId`, `AttemptId`, `ProviderRequestId`,
  `ToolCallId` — each a distinct `String` wrapper (`Display`,
  `Serialize`/`Deserialize` as `#[serde(transparent)]`, `From<&str>`,
  `From<String>`). Distinct Rust types, not a shared alias, so a `StepId`
  cannot be passed where a `MissionId` is expected — a compile-time
  property (`distinct_id_types_are_not_interchangeable_at_the_type_level`
  documents this as a witness test, since the compiler enforces it and a
  runtime test cannot).
- `CorrelationContext`: `mission_id` (required) plus four `Option<_>`
  narrowing fields. Builder methods (`for_mission`, `with_step`,
  `with_attempt`, `with_provider_request`, `with_tool_call`) enforce the
  hierarchy order at construction time — `with_attempt` fails
  `CorrelationError::AttemptWithoutStep` if no step is set yet, and so on
  down the chain. `validate()` re-checks the same rule defensively for
  contexts assembled by struct literal (e.g. off a deserialized record)
  rather than the builder.
- `event::EventContext` is now `pub type EventContext =
  correlation::CorrelationContext` — the event log does not define its
  own scheme; it reuses this one. `Event::computed_hash` needed no
  change: it already serializes `self.context` generically, so the hash
  is automatically sensitive to every level of correlation now carried,
  including `provider_request_id`/`tool_call_id` which did not exist
  before.
- The three pre-existing struct-literal construction sites (`event.rs`,
  `event_log.rs`, `chain_anchor.rs` test modules) updated to the builder
  API (`EventContext::for_mission(..)`, `.with_step(..)`).

## Tests (11 new, all passing)
`correlation.rs`: `full_hierarchy_builds_in_order`,
`mission_only_context_is_valid`,
`mission_and_step_without_attempt_is_valid`,
`attempt_without_step_is_rejected`,
`provider_request_without_attempt_is_rejected`,
`tool_call_without_provider_request_is_rejected`,
`validate_catches_hand_assembled_skip_of_every_level` (all three skip
cases independently, not just the first one found),
`json_round_trip_preserves_full_hierarchy`,
`json_omits_absent_levels`,
`distinct_id_types_are_not_interchangeable_at_the_type_level`.
`event.rs`: `event_context_carries_full_hierarchy_and_hash_is_sensitive_to_it`
— two events with identical everything except `tool_call_id` produce
different `event_hash`; the same context reproduces the same hash
deterministically.

## Verdict
Both `done_when` criteria met:
1. "mission→step→attempt→event→provider_request→tool_call threading" —
   `CorrelationContext` carries all five levels; `EventContext` is that
   type; `event_context_carries_full_hierarchy_and_hash_is_sensitive_to_it`
   proves an event can carry the full chain and that the chain is part of
   what's hashed.
2. "no independent ad hoc ID systems introduced" — one type per level,
   defined once in `correlation.rs`, reused by `event.rs` via type alias;
   pre-existing unrelated identifiers (`intent_id`, `chain_id`) were
   audited and left alone as genuinely out of scope, not folded in or
   duplicated.
ACCEPTED.
