## Design decision stated up front (load-bearing, flagged per Build Protocol §8)

`schema_version` is a sibling of a record's content (`Versioned<T>`, `#[serde(flatten)]`), never a field inside `Event` or `Anchor`, and **never an input to `Event::computed_hash()` or `Anchor::computed_hash()`**. Rationale: if it were, a future v1→v2 migration would change a record's hash even though its semantic content didn't move, silently breaking every downstream `previous_event_hash` link that already committed to the old hash. `event.rs` was not touched at all this task — confirmed by `git diff --stat` (7 files changed, `event.rs` not among them) — so there is zero risk of an accidental hash-computation change hiding in this task.

## Audit-before-implementation, per instruction ("do not assume one field on one struct covers every record")

Enumerated every actual persisted record type before writing code: `Event` (event_log.rs, JSONL), `Anchor` (chain_anchor.rs, JSONL), and three `AtomicStore`-backed whole-file JSON stores (`OutboxState`, idempotency `StoreState`, `AllocatorState`). Wired versioning into `AtomicStore::update` once, which automatically covers all three whole-file stores — but then found **three additional bypass read paths that skip `AtomicStore::update` entirely** and would have silently skipped version checking if left alone: `SequenceAllocator::current()`, `IdempotencyStore::read_state()`, and (found only during this audit, not anticipated going in) `Outbox::pending()` / `Outbox::get()`. All five now route through a shared `persist::read_versioned()` helper so there's exactly one place version-checking logic lives, not five copies that could drift.

## Real failures found and fixed while verifying (not weakened, not skipped)

Two pre-existing tamper-detection tests broke on first full-suite run after wiring versioning in:

- `event_log::tests::tampering_with_history_is_detectable_end_to_end`
- `chain_anchor::tests::mutated_historical_event_fails_closed`

Root cause: both tests simulate an attacker editing a JSONL line by parsing it into a bare `Event`, mutating a field, and re-serializing the bare struct — which doesn't know about `schema_version` and so silently drops it, producing a line no real in-place edit would ever actually leave behind. Fixed by routing the test's own parse/reserialize step through `schema::decode_versioned`/`encode_versioned` (the same functions the log itself uses), which preserves the key exactly as a real tamper would. This is a fix to test fidelity, not a weakened assertion — both tests still assert the exact same tamper-detection property they did before.
