# VG-P3-W04-T01 — Scenario Execution

**Task:** P3-W04-T01 — Connect the phase's failure scenarios to the
Blueprint's Scenario DSL / simulator machinery (Phase Manifest §7.3
P3-W04; Blueprint §28.4).

**Status:** ACCEPTED

## Starting condition
Nothing in the crate implemented the Scenario DSL or an execution engine;
confirmed by grep before writing any code.

## Implementation
New module `PROJECT/crates/conductor-kernel/src/scenario.rs`:

- `Scenario`/`ScenarioStep` are the Rust shape of Blueprint §28.4's YAML
  DSL (`setup.files`, `attempt.behavior`, `expected.reconciliation`).
  `Scenario` derives `serde::{Serialize, Deserialize}` so it can be
  loaded from a file format later without a redesign — but `behavior` is
  `#[serde(skip)]`, documented explicitly in code: `FakeBehavior`
  (already-accepted `provider.rs`) doesn't itself derive
  `Serialize`/`Deserialize`, so this field cannot round-trip yet. A real
  limitation, stated rather than left implicit.
- `run_scenario` actually executes: real temp workspace, real setup
  files, real `Baseline::capture` (P2-W02), each `ScenarioStep` run in
  order (a failing `ProviderBehavior` genuinely stops the remaining
  steps — the interruption is real, not simulated by skipping ahead),
  real re-capture, real `reconcile()` (P2-W03) **and** real
  `check_merge_safety()` (P2-W06).
- **Bug found and fixed during this session's own verification, not
  papered over:** the first version of the engine only called
  `reconcile()`. `cargo test` caught `changed_baseline_family` failing —
  reconcile() alone reported `ExpectedChange` for a scenario the test
  expected to be `UnexpectedChange`, because reconcile() has no way to
  see that the "expected" file was in fact changed by a *user*, not the
  attempt. This was a real design gap, not a wrong test value to patch
  around: several required failure families (changed baseline, merge
  conflict, and — more subtly — user conflict, where `reconcile()` alone
  can look misleadingly clean even though the merge-time re-check must
  still catch it) are fundamentally about Invariant 13's merge-time
  re-check (`conflict.rs::check_merge_safety`), not `reconcile()`'s
  whole-file classification. Fixed by having the engine run **both** real
  checks and having `Scenario`/`ScenarioResult` carry `expected_merge_safe`/
  `merge_check` so scenarios can assert on whichever check is actually
  relevant to what they're testing. `user_conflict_family`'s comment now
  explains this directly: it's the concrete demonstration of *why* the
  two-phase merge check exists as a safety net over reconcile()'s
  potentially-optimistic read.

## Blueprint's own worked example
`blueprint_worked_example_timeout_after_partial_edit` reproduces
Blueprint §28.4's literal YAML example (`edit: App.tsx`, then `timeout`)
and asserts the actual outcome equals the Blueprint's own stated expected
outcome, `PartialChange` — the strongest single proof this task can offer
that the DSL and engine are faithful to the spec, not just to this task's
own invented examples.

## All 17 required failure families covered
Every family in Phase Manifest §7.4 has at least one real, executed,
asserted scenario: `timeout`, `disconnect`, `delayed_response`,
`rate_limited_429`, `quota_exhaustion` (documented: no `FakeBehavior`
represents this directly; closest representation is `ProviderResult.quota_info`,
not mechanically produced by any behavior — stated explicitly, not
assumed), `server_error_5xx` (documented: `Crash` is the closest available
`FakeBehavior`, no new variant added to the already-accepted `provider.rs`),
`malformed_response`, `invalid_tool_request`, `partial_edit`,
`process_termination`, `persistence_interruption`, `checkpoint_interruption`
(all three: abort-marker treatment, same as `chaos.rs` already established
— no real attempt-execution orchestrator exists to interrupt further),
`duplicate_response`, `ambiguous_provider_outcome` (documented: `Timeout`
is the closest representable case; Blueprint §10.5's full
`IdempotencySupport` resolution pipeline isn't built by any task yet),
`user_conflict`, `changed_baseline`, `merge_conflict`.
