# VG-P4-W04-T01 — Protected Success Transition

**Task:** P4-W04-T01 — Prove: Only Verification Engine → AttemptStatus::Succeeded
(Phase Manifest §8.3 P4-W04, §8.4, §8.5; Blueprint §7, §8; Invariant 14).

**Status:** ACCEPTED

## What this task closes
`state.rs`'s gate has restricted the `Succeeded` edge to
`TransitionActor::VerificationEngine` since Phase 1, re-confirmed at
P2-W04. That answers *who* may call it. Nothing until now answered the
other half: does the one caller who's authorized only call it when it's
actually been earned. This task composes P4-W01's pipeline, P4-W02's
evidence, and P4-W03's Mission Acceptance Contract evaluation into one
decision, and proves — against the real `state.rs` gate, not a
simulated one — that the decision only reaches `Succeed` when every one
of Phase Manifest §8.4's eight required scenarios genuinely warrants it.

## Implementation
New module `PROJECT/crates/conductor-kernel/src/verification_engine.rs`:

- `decide(pipeline_result, contract, mac_evaluation, evidence_by_criterion_id)`
  composes all three already-accepted modules' outputs into a single
  `SuccessDecision`.
- **Two checks added on top of P4-W02/P4-W03, not inside them**
  (neither module was reopened): `verification_type_expects` maps a
  criterion's declared verification method to the observation type its
  evidence must have come from (the "wrong verification method" check),
  and every blocking criterion's evidence must be
  `IntegrityLevel::IndependentlyVerified`, never merely `SelfReported`
  (the "false model success" check — mirroring the rule P4-W01 already
  established for `RequirementVerificationClass::ModelAssisted`). Both
  are explicitly flagged, in the module doc comment and the task
  contract, as this task's own reasoned additions — Blueprint §8's JSON
  schema doesn't literally include either as a `required_evidence`
  field.
- `attempt_succeeded_transition` calls the real
  `state::try_attempt_transition(TransitionActor::VerificationEngine, Running, Succeeded)`
  exactly once, inside the `Succeed` branch only — the `Fail` branch
  returns before reaching that call at all.

## The eight required scenarios (Phase Manifest §8.4), each its own test
`passing_acceptance_criteria_reaches_a_real_succeeded_transition` —
proven against the **real** `state.rs` gate: `attempt_succeeded_transition`
returns a genuine `Ok(())`, not a simulated one.
`failing_acceptance_criteria_never_reaches_succeeded`,
`stale_evidence_never_reaches_succeeded`,
`insufficient_evidence_never_reaches_succeeded`,
`wrong_verification_method_never_reaches_succeeded` (asserts the specific
reason string, not just that it failed),
`partial_completion_never_reaches_succeeded` (a real `PartialChange`
reconciliation outcome, via P4-W01's pipeline, genuinely produced by two
declared-expected files where only one landed),
`false_model_success_never_reaches_succeeded` (asserts the specific
reason string),
`a_favorable_reconciliation_alone_never_reaches_succeeded_without_full_mac_verification` —
directly confirms the diff-verification stage genuinely passed
(`StageStatus::Passed`, not assumed) while no MAC evidence existed at
all, and that this combination still fails: a favorable diff alone is
proven insufficient, not just asserted to be.

A ninth test, `model_assisted_pipeline_requirement_still_cannot_alone_satisfy_blocking`,
re-confirms P4-W01's `ModelAssisted` rule still holds when composed
through the full pipeline, not just in isolation.
