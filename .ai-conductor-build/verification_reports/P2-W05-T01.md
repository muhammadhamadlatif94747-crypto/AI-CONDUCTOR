# VG-P2-W05-T01 — Mutation Attribution

**Task:** P2-W05-T01 — Implement mutation attribution per Blueprint §4.6.

**Status:** ACCEPTED

## Starting condition
P2-W03's `reconcile()` classifies whole files (`ExpectedChange`,
`UnexpectedChange`, etc.) but cannot answer "did the AI change line 40, or
did the user" when both touch the same file — confirmed by reading
`reconciliation.rs` before writing any code; nothing at line-region
granularity existed anywhere in the crate.

## Implementation
New module `PROJECT/crates/conductor-kernel/src/mutation_attribution.rs`:

- `RegionClassification` reproduces Blueprint §4.6's four categories
  verbatim (`ExpectedConductorChange`, `UnexpectedAiChange`, `UserChange`,
  `ConflictRegion`).
- `attribute_mutations(path, baseline, ai_result, live_current, expected)`
  runs real `git diff --no-index --unified=0` twice — baseline→ai_result
  and baseline→live_current — both anchored to the same baseline line
  numbers, which is what makes direct region-overlap comparison between
  the two diffs meaningful. A region touched only in the AI diff
  classifies as `ExpectedConductorChange`/`UnexpectedAiChange` depending
  on whether the file is in `expected.files` (reusing P2-W03's
  `ExpectedOperation` rather than inventing a second file-scope concept);
  touched only in the user diff → `UserChange`; touched in both, with
  overlapping baseline ranges → `ConflictRegion`.
- **No custom diff algorithm.** Consistent with the crate's established
  discipline (P2-W01's real `git worktree`), hunks come from real `git
  diff` output, parsed from its actual `@@ -start[,count] +...@@` header
  format (verified against real git output in this sandbox before writing
  the parser, not assumed from memory of the format).
- **Conservative pure-insertion handling:** a `-N,0` hunk (nothing removed
  from baseline, pure insertion) is widened to a single-line overlap
  window at its anchor line rather than treated as zero-width. This is a
  deliberate, documented choice in the direction that can only cause an
  extra region to be flagged `ConflictRegion` that a stricter reading
  might not — never the reverse. Under-flagging a real conflict is exactly
  what Invariant 11 (no silent auto-resolution) forbids.

**Scope boundary held deliberately:** this task classifies from three
already-available content snapshots. It does not decide what to do about a
`ConflictRegion` (P2-W06's halt policy) and does not implement how a real
caller obtains those three snapshots from a running attempt's lifecycle
(P2-W07/Phase 5 orchestration) — noted explicitly rather than silently
assumed solved.

## Tests (10 new, all passing)
`no_changes_anywhere_is_an_empty_result`,
`ai_only_change_in_an_expected_file_is_expected_conductor_change`,
`ai_only_change_in_an_unexpected_file_is_unexpected_ai_change`,
`user_only_change_is_user_change`,
`overlapping_regions_are_conflict_region`,
`disjoint_regions_in_the_same_file_are_not_a_conflict` (proves two
non-overlapping edits in the same file are NOT misclassified as a
conflict),
`adjacent_pure_insertions_at_the_same_baseline_line_are_treated_as_a_conflict`
(directly exercises the conservative pure-insertion rule, not just
asserted in a comment),
`insertions_at_different_baseline_lines_are_not_a_conflict`,
`baseline_range_is_reported_in_baseline_line_coordinates`,
`path_is_carried_through_to_the_result`. Every test runs real `git diff
--no-index` against real temp files — nothing mocked or hand-written as
synthetic diff text.
