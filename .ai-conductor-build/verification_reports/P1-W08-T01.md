# VG-P1-W08-T01 — Monotonic Sequence Allocator

**Task:** P1-W08-T01 — Monotonic sequence-number allocator (Blueprint
§4.9 / §20, Phase Manifest P1-W08).

**Status:** ACCEPTED

## Implementation
`PROJECT/crates/conductor-kernel/src/sequence.rs` — `SequenceAllocator`,
built on the P1-W05 `AtomicStore`. Persisted state is a single integer
(`last_issued`). `next()` is one atomic `AtomicStore::update` call;
`current()` reads it back without allocating.

## Why this is separate from event_log.rs's existing sequencing
`event_log.rs` already derives a running counter from the log file
itself (recovered by reading the tail on open) — that covers sequence
numbers *for events specifically*. This allocator is a standalone,
independently durable source for callers that need a number before the
record carrying it is fully built (e.g. threading `sequence_number`
through a multi-step outbox intent), per the Blueprint's phrasing:
"feeds `sequence_number` in Section 4.9" — a feeder, not a replacement.

## Crash-mid-allocate proof (the task's specific hard requirement)
Because `AtomicStore` already collapses "reserve" and "commit" into one
atomic temp-file-write + rename, there are only two possible outcomes of
a crash during `next()`, never a third — enumerated in the module docs.
`tests::crash_mid_allocate_never_duplicates_or_rolls_back_on_restart`
proves this directly: two numbers are durably issued (1, 2), then an
orphaned sibling temp file is created on disk with content that was
never renamed onto the real path (reproducing exactly what a crash
between "temp file written" and "rename" would leave behind). The test
asserts the real file is untouched (still `last_issued: 2`), then opens
a fresh allocator and confirms the next call returns exactly 3 — not a
rollback to a repeat of 2, not a corrupted jump to 4.
