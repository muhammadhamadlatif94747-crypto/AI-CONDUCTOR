## Key proofs
- **Atomicity under simulated crash**: `target_is_never_touched_before_the_final_rename` — the one test that actually matters for this task — manually performs the create+write+fsync steps and *withholds* the rename (the simulated crash point), then asserts the target still holds its original, complete content. This is a structural proof, not a timing-dependent one: the code path literally never opens the target for writing.
- **No lost update under real concurrency**: 64 OS threads, one `AtomicStore`, each pushes its own id; final ledger contains all 64 exactly once. Re-run 5× with zero flakiness.
- **Fail-closed on corrupt existing data**: `corrupt_existing_file_surfaces_as_error_not_silent_data_loss` — a store update on top of a garbage file returns `PersistError::Serde`, never silently treats corruption as "empty."
- **Directory auto-creation**: nested target paths work without a separate mkdir step, matching how a real mission/step/attempt hierarchy would be laid out on disk.

## Explicit scope limit (stated, not hidden)
`AtomicStore::update` serializes writers **within one process** sharing the same handle. It does not arbitrate two separate OS processes writing the same path (that needs an OS-level file lock/advisory lock, not an in-process `Mutex`). F-0001's actual failure was exactly this — two same-process tool calls, in-process — so this is a correct fix for the recorded root cause, not a partial one; multi-process contention is a different, not-yet-encountered failure mode and is out of scope for P1-W05 as contracted. Documented in the module doc comment as a follow-on rather than silently assumed away.
