# VG-P4-W03-T01 — Mission Acceptance Contracts

**Task:** P4-W03-T01 — Enforce Mission Acceptance Contracts before an
Attempt may become Succeeded (Phase Manifest §8.3 P4-W03, §8.5;
Blueprint §8).

**Status:** ACCEPTED

## Starting condition
Nothing in the crate implemented the Mission Acceptance Contract schema
or any enforcement logic; confirmed by grep before writing any code.
P4-W02's `Evidence`/`Evidence::matches` existed as the real primitive this
task's enforcement reuses directly.

## Implementation
New module `PROJECT/crates/conductor-kernel/src/mission_acceptance.rs`:

- `VerificationType` reproduces exactly the five variants Blueprint §8's
  own worked full-contract example names (`dom_check`, `test_command`,
  `integration_test`, `test_suite_diff`, `diff_scope_check`) — the
  concrete, complete set the text actually provides, not extended with
  plausible-sounding additions. `ExpectedResult::Other(String)` is
  explicitly flagged as this task's own fallback beyond the single shown
  example (`exit_code_0`).
- `Criterion`/`MissionAcceptanceContract`/`RequiredEvidenceSpec` match
  Blueprint §8's JSON shape field-for-field. `RequiredEvidenceSpec`
  reuses P4-W02's `EvidenceProvenance` directly rather than a second
  provenance concept.
- `evaluate_contract` reuses `Evidence::matches` (P4-W02) directly for
  each criterion's check — no second provenance/freshness comparison
  reimplemented. A criterion with no corresponding evidence entry fails
  explicitly as `CriterionOutcome::NoEvidenceProvided`, never silently
  treated as satisfied.
- `MacEvaluationResult` distinguishes `NoEvidenceProvided` from
  `EvidenceDidNotMatch` per criterion — proven directly by
  `no_evidence_and_non_matching_evidence_are_distinguishable_outcomes`,
  not assumed. This is what makes Blueprint §8's "specific unmet criteria
  become the next repair request, never a vague 'try again'" concrete: a
  future caller gets real information about *why* something failed, not
  just that it did.
- `all_blocking_satisfied()` only considers `blocking: true` criteria;
  proven directly against a case constructed to look identical to a
  failing blocking one if the blocking/non-blocking distinction were
  dropped (`a_non_blocking_criterion_failure_does_not_fail_the_contract`).

**Scope boundary held deliberately:** this module produces a
`MacEvaluationResult`. It never references `AttemptStatus` anywhere in
its logic (confirmed by grep — the only hit is in the module's own doc
comment explaining the boundary). It does not modify P4-W01's already-
accepted `verification.rs` pipeline to adopt this richer schema — that
module's own contract explicitly deferred the full MAC schema to this
task; wiring the two together is left for a future orchestration
decision, consistent with the established discipline of not reopening
accepted modules without a specific need.

## Blueprint's own worked example
`blueprint_worked_example_seven_criterion_auth_contract` reproduces
Blueprint §8's own seven-criterion "auth" mission literally (`auth-01`
through `auth-07`, with their stated verification types and provenances)
and evaluates it end to end against matching evidence — the strongest
single proof this task can offer that the schema and enforcement are
faithful to the spec, not just to this task's own invented examples.
