# VG-P3-W03-T01 — Chaos Mode

**Task:** P3-W03-T01 — Implement deterministic chaos injection; must
include simulated mid-attempt user edits (Phase Manifest §7.3 P3-W03;
Blueprint §10.4).

**Status:** ACCEPTED

## Starting condition
Nothing in the crate implemented chaos injection; confirmed by grep
before writing any code. `FakeProvider` (P3-W01) and `Baseline`/
`check_merge_safety` (P2-W02/W06) existed as the primitives this task
would compose.

## Implementation
New module `PROJECT/crates/conductor-kernel/src/chaos.rs`:

- `ChaosCategory` reproduces Blueprint §10.4's eight categories verbatim,
  with `default_weight_percent` matching the Blueprint's percentages
  exactly (10/10/5/15/5/5/5/5).
- `ChaosConfig` carries `chaos_seed`/`scenario_id`/`virtual_time_seed` —
  Blueprint §10.4's hard rule ("every chaos run records these three...
  random chaos without a recorded seed is chaos you cannot debug") —
  plus per-category weights, defaulting to the Blueprint values via
  `with_default_weights` and overridable via `set_weight_percent`.
- `ChaosEngine::roll` evaluates each category as an *independent* trial
  (not a mutually-exclusive partition of one roll), matching Blueprint
  §28.5's own composite-scenario example, which combines multiple
  simultaneous chaos events in one scenario. Backed by a small,
  self-contained `splitmix64` PRNG — no new external randomness
  dependency, since exact seeded reproducibility is the only property
  actually needed, and a general-purpose crate wouldn't provide that any
  more reliably.
- `ChaosCategory::to_fake_behavior` maps the four provider-adapter-layer
  categories to concrete `FakeBehavior` variants (P3-W01).
  `ProcessTermination`/`CheckpointInterruption`/`StatePersistenceInterruption`
  deliberately return `None` — no attempt-execution orchestrator exists
  yet for those to mechanically interrupt (the same gap every P2 task
  since W06 independently confirmed); they exist in the enum for
  Blueprint-checklist fidelity, not mechanically simulated here.
- `simulate_user_edit_mid_attempt` is Phase Manifest's explicitly
  required category, made concrete: deterministically appends a
  seed-derived marker line to a real file in a real workspace.

## The required proof
Phase Manifest §7.3 P3-W03 doesn't just ask for the category to exist —
it's called out because it's supposed to exercise Conflict detection.
`tests::simulated_user_edit_mid_attempt_triggers_conflict_detection`
proves this end to end, not as an isolated unit test: captures a real
`Baseline`, runs `simulate_user_edit_mid_attempt`, re-captures, runs
P2-W06's `check_merge_safety`, and asserts the result is `Conflict` with
the exact changed path — composing three separate tasks' work (P2-W02,
P2-W06, P3-W03) into one real, passing proof.
