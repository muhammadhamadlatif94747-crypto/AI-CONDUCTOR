# VG-P4-W01-T01 — Verification Pipeline

**Task:** P4-W01-T01 — Implement the full verification pipeline defined
by Blueprint Section 7 (Phase Manifest §8.3 P4-W01; Blueprint §7, §7.1).

**Status:** ACCEPTED

## ⚠ Read this before anything else in this report

This task's own subject matter is a security boundary, not just
reliability logic. **The command sandbox built here is PARTIAL and must
not be treated as secure against an adversarial or untrusted command.**
Blueprint §7.1 requires OS-level process-tree containment (Windows job
objects / Unix namespaces or cgroups) validated by a dedicated
escape-attempt test suite. This task does not implement that — it was
explicitly scoped out (see the task contract's `forbidden_actions`) as a
substantial, platform-specific systems-security undertaking that
deserves its own dedicated task with proper per-platform validation,
rather than being rushed as a sub-component of the pipeline. This gap is
restated in the module's own doc comment, in the task contract, and here,
on purpose, more than once — it should not be possible to read only one
of the three and miss it.

## Starting condition
Nothing in the crate implemented the Verification Engine pipeline or any
form of command sandboxing; confirmed by grep before writing any code.

## Implementation
New module `PROJECT/crates/conductor-kernel/src/verification.rs`:

- `VerificationStage` reproduces Blueprint §7's eight stages verbatim, in
  order. `run_pipeline` executes them with genuine short-circuiting: a
  failed stage causes every later stage to report
  `SkippedDueToEarlierFailure` rather than running — proven directly
  (`a_failed_build_skips_every_later_stage`,
  `a_failed_requirement_verification_skips_the_mac_check`), not merely
  documented as intended.
- `RequirementVerificationClass` reproduces Blueprint §7's three
  variants verbatim. `Requirement::is_satisfied` never reads
  `raw_result` for `ModelAssisted` — structurally, not via a runtime
  check that could be bypassed, matching this crate's established
  pattern (`recommended_attempt_status` returning `None` for
  `ExpectedChange`, `PersonDecision` having no auto-resolve variant).
  Proven by `model_assisted_alone_cannot_satisfy_a_blocking_requirement`
  with `raw_result: true` specifically, so the test can't pass by
  accident.
- `run_verification_command` implements four of Blueprint §7.1's
  protections for real, against real process execution, each with a
  dedicated test:
  - **Command allowlist** — only recognized build/test/lint runner
    prefixes; anything else rejected before spawning.
  - **Working-directory confinement** — canonicalized and checked to be
    inside the given worktree root.
  - **A real timeout** — a poll-loop against `Child::try_wait()` with a
    deadline, killing the child if exceeded. Documented explicitly as
    killing the immediate child only, not its full descendant process
    tree (that needs the OS-level containment this task doesn't build).
  - **Environment filtering** — `Command::env_clear()` plus an explicit
    allowlist (`PATH`, `HOME`, etc.), so anything not named — including
    anything a future Credential Vault would manage — is never inherited
    by the child at all.
  - **Mutation detection** (for commands marked read-only-intended) —
    reuses P2-W02's `Baseline::capture`/`diff` directly: if a command
    that claimed not to touch the workspace did anyway, that's a real,
    caught `SandboxError::UnexpectedMutation`.
  - **Not implemented, not claimed:** OS-level process-tree containment,
    network isolation.

## A real bug found and fixed before any test ran against real processes
Before writing the sandbox tests, I discovered `run_verification_command`'s
original argument parsing used `command_line.split_whitespace()`, which
mangles any quoted argument containing spaces (e.g.
`npx -y -c "sh -c 'sleep 5'"` would be split into seven broken fragments
instead of four real tokens). This wasn't caught by a failing test —it was
caught by manually verifying the exact `npx` invocation pattern in a real
shell *before* trusting it in Rust, per this session's established
discipline of never assuming an external tool's behavior without checking
it directly. Fixed by writing a small, self-contained, quote-aware
tokenizer (`tokenize_command_line`) rather than adding a shell-parsing
dependency — tested directly with five dedicated unit tests
(`tokenizer_*`), not only indirectly through the sandbox tests that
happen to use it.

Pipeline: `all_pass_reaches_checkpoint_accepted`,
`a_failed_build_skips_every_later_stage`,
`a_failed_requirement_verification_skips_the_mac_check`,
`diff_not_matching_expected_operation_fails_the_diff_verification_stage`.

`machine_verifiable_and_human_verifiable_use_their_real_result`.
Tokenizer: `tokenizer_splits_plain_whitespace_separated_words`,
`tokenizer_keeps_a_double_quoted_argument_with_spaces_as_one_token`,
`tokenizer_preserves_single_quotes_nested_inside_double_quotes`,
`tokenizer_preserves_escaped_double_quotes_inside_a_double_quoted_token`,
`tokenizer_returns_empty_for_an_empty_or_whitespace_only_command`.
Sandbox (real process spawns, real `npx`/`sh`, no mocking):
`command_allowlist_rejects_an_unrecognized_command`,
`working_directory_outside_the_worktree_is_rejected`,
`a_long_running_command_is_killed_by_the_timeout` (a real 5-second sleep,
killed within a 200ms timeout, total elapsed time asserted under 3s),
`environment_filtering_hides_an_arbitrary_var_from_the_child` (a real env
var set on the test process, checked from inside the real spawned child
that it is genuinely absent), `mutation_detection_catches_a_read_only_command_that_writes`
(a real file write by a command marked read-only, caught).
